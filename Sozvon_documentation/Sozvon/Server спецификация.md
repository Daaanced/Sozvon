## "Функции рабочего MVP:"

## 1. **Сервер авторизации и управления пользователями**

Функции:

Регистрация пользователя

- принимает **логин**, **пароль**, необязательно email
- проверяет уникальность логина
- хэширует пароль (bcrypt/argon2)
- сохраняет запись в базе

Авторизация (логин)

- принимает логин и пароль
- сравнивает хэш
- выдаёт **JWT** или session token

Выдача UID

При регистрации генерируется уникальный идентификатор:

- `UUIDv4` или `snowflake`, или просто автоинкремент ID

_UID нужен для поиска контактов и для вызовов._

## 2. **Система поиска пользователей / списка контактов**

### Функции:

### ✔ Поиск по логину или UID

Клиент отправляет строку, сервер возвращает:

- UID
- логин
- статус (online/offline)

### ✔ Добавление контактов (опционально)

Если твой UX предполагает «добавить в друзья»:

- отправка заявки
- принятие/отклонение
- хранение списка контактов

Если нет — можно отложить.

## 3. **Сервер обмена текстовыми сообщениями**

Это простой компонент.

Функции:

WebSocket-подключение

Каждый клиент открывает WS-соединение после логина.

Отправка сообщения другому пользователю

Сервер выполняет:

- принимает сообщение от клиента
- проверяет токен
- определяет, онлайн ли получатель
- если онлайн → пересылает по его WebSocket
- если оффлайн → сохраняет в базу

### ✔ История сообщений

Простая таблица:

- sender_id
- receiver_id
- timestamp
- text

---

## 4. **Сервер сигнализации для WebRTC звонков**

Сервер **НЕ передаёт аудио/видео**, это делает P2P WebRTC.  
Но сервер обязан выполнять «держатель переговоров».

### Обязательные функции:

Установление WebSocket сессии (та же, что для чата)

Используется один WebSocket для:

- текстовых сообщений
- уведомлений о звонках
- сигнализации WebRTC

Передача сигнализационных сообщений:

- `offer`
- `answer`
- `ICE candidates`

Сервер просто пересылает JSON от клиента А → к клиенту B.

## 5. **STUN сервер**

Чтобы WebRTC мог работать через NAT.

Варианты:

- использовать готовый: `stun:stun.l.google.com:19302`
- поднять свой (Pion STUN / Coturn)

На этапе MVP можно _**вообще не запускать свой STUN**_.

## 6. **TURN сервер (только для плохих сетей)**

TURN — дорогой по трафику, потому что передаёт весь медиапоток.  
Для начала можно не разворачивать, но для будущего нужен.

Лучшее решение: Coturn.

## 7. **Состояние пользователей (presence)**

Сервер должен знать:

- кто сейчас онлайн
- кому можно направить звонок
- кому можно отправить WS-сообщение

Когда клиент входит:

- открывает WS
- сервер помечает его online

Когда выходит:

- закрывает WS
- сервер помечает offline

# Более краткая версия

### 🔹 **1. Авторизация:**

- регистрация (логин, пароль → DB)
- логин (JWT выдача)

### 🔹 **2. Пользователи:**

- поиск по логину
- поиск по UID
- получение информации о пользователе
- (опционально) добавление в контакты

### 🔹 **3. WebSocket сервер:**

- хранение списка подключённых клиентов
- пересылка текстовых сообщений онлайн-пользователям
- сохранение оффлайн-сообщений

### 🔹 **4. WebRTC сигнализация:**

- пересылка offer
- пересылка answer
- пересылка ICE candidates
- отправка уведомлений «входящий вызов»

### 🔹 **5. STUN / TURN (по возможности):**

- STUN можно использовать публичный
- TURN рекомендуется позже

### Как это работает в реальности (короткая схема)

1. Клиент А хочет звонить пользователю B
2. Клиент А отправляет WebSocket-сообщение:  
   `{type: "call_request", to: B}`
3. Сервер пересылает B
4. B отвечает
5. А и B обмениваются offer/answer через сервер
6. А и B обмениваются ICE-кандидатами
7. Соединение WebRTC установлено → P2P поток начался

Сервер больше не участвует.
