# Auth Service — техническая документация

Микросервис **Sozvon**, отвечающий за регистрацию пользователей, проверку учетных данных и управление аутентификацией.

Хранит учетные данные в собственной PostgreSQL-базе и после успешной регистрации или входа выдает клиенту **JWT-токен**, который используется для доступа к защищенным ресурсам системы.

Реализован как самостоятельное HTTP-приложение, взаимодействующее с другими микросервисами Sozvon — прежде всего с **User Service** и **Chat Service**.

---

## 1. Место в архитектуре Sozvon

```
                ┌───────────────┐
                │     Client    │
                └───────┬───────┘
                        │ HTTP
                        ▼
                ┌───────────────┐
                │  Auth Service │
                └───┬───────┬───┘
                    │       │
             PostgreSQL     │ HTTP
                    │       ▼
                    │   ┌───────────────┐
                    │   │  User Service │
                    │   └───────────────┘
                    │
                    │ HTTP
                    ▼
               ┌───────────────┐
               │  Chat Service │
               └───────────────┘
```

Auth Service **не объединяет базы всех сервисов в одну БД**, а взаимодействует с ними через HTTP API.

**Разделение ответственности:**
- **Auth Service** — authentication: подтверждение того, что пользователь владеет учетной записью (`login` + `password`, JWT).
- **User Service** — профиль (`name`, `picture`, `info` и т. д.).
- **Chat Service** — членство пользователя в чатах.

## 2. HTTP API

| Метод / путь | Описание |
|---|---|
| `POST /api/auth/register` | Регистрация пользователя |
| `POST /api/auth/login` | Авторизация (вход) |
| `GET /api/auth/validate` | Проверка JWT |
| `DELETE /api/auth/users/{login}` | Каскадное удаление пользователя |
| `GET /api/health` | Health check |

### 2.1 Регистрация

`POST /api/auth/register`:

1. принять логин и пароль;
2. проверить корректность входных данных;
3. проверить, существует ли пользователь;
4. захешировать пароль через **bcrypt**;
5. сохранить пользователя в PostgreSQL;
6. создать профиль через **User Service**;
7. сформировать JWT;
8. вернуть токен клиенту.

**Откат при ошибке:** если профиль в User Service создать не удалось — учетная запись удаляется из Auth Service.

```
	Client
	↓
	Auth Service
	├── PostgreSQL   → сохраняет login + bcrypt password
	└── User Service → создает профиль
	↓
	JWT
	↓
	Client
```

### 2.2 Авторизация

`POST /api/auth/login`:

1. получить пользователя по логину из PostgreSQL;
2. сравнить введенный пароль с bcrypt-хешем;
3. получить имя пользователя из User Service;
4. сгенерировать JWT;
5. вернуть токен клиенту.

Пароль пользователя **не хранится в открытом виде**.

```
	Client
	↓
	Auth Service
	├── PostgreSQL   → получает bcrypt hash
	├── bcrypt       → проверяет пароль
	└── User Service → получает имя
	↓
	JWT
	↓
	Client
```

### 2.3 Проверка JWT

`GET /api/auth/validate` — принимает токен из `Authorization: Bearer ...`, проверяет подпись и срок действия, возвращает claims: логин, имя пользователя, время истечения токена.

**Состав JWT** (алгоритм `HS256`):

```
user_id
login
name
issued_at
expires_at
issuer
subject
```

### 2.4 Удаление пользователя

`DELETE /api/auth/users/{login}` — каскадное удаление по цепочке:

```
Auth Service → User Service → Chat Service → Auth DB
```

Из Chat Service дополнительно удаляются связанные записи пользователя в `chat_members`.

### 2.5 Health check

`GET /api/health`:

```json
{
  "status": "ok",
  "service": "authorization"
}
```

## 3. База данных

- PostgreSQL — хранение учетных записей.
- `database/sql` + `lib/pq` — работа с БД.
- Connection pool: `MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`.
- Автоматическая проверка и создание таблицы `users`.
- Поддержка начального заполнения БД из SQL dump (`db/authdb_dump.sql`).

**Схема таблицы `users`:**
```
id
login
password
created_at
updated_at
```

---

## 4. Межсервисное взаимодействие

Для обращения к другим сервисам используются:

- стандартный `net/http`, JSON;
- отдельные HTTP-клиенты — `UserServiceClient` и `ChatServiceClient`;
- connection pooling через `http.Transport`;
- timeout на межсервисные запросы;
- **retry-механизм** при создании профиля — до **3 попыток** с увеличением задержки между ними.

---

## 5. Безопасность

| Механизм | Назначение |
|---|---|
| bcrypt | безопасное хеширование паролей |
| JWT | авторизация и передача claims |
| HS256 | алгоритм подписи JWT |
| Ограничение времени жизни токена | предотвращает бессрочное использование JWT |
| Проверка `Authorization: Bearer` | извлечение и валидация токена |
| Валидация входных данных | защита от некорректных запросов |
| Таймауты HTTP-запросов | защита от зависших соединений |

---

## 6. Надежность

- **Logging middleware** — логирование HTTP-запросов;
- **Recovery middleware** — перехват panic;
- **Graceful shutdown** при `SIGINT`/`SIGTERM`;
- таймауты подключения и обработки запросов;
- контекстные ограничения времени выполнения операций (`context`);
- проверка состояния БД при запуске.

---

## 7. Конфигурация

Настройки вынесены в переменные окружения:

- параметры PostgreSQL;
- адрес HTTP-сервера;
- JWT secret и время жизни токена;
- адреса User Service и Chat Service;
- таймауты;
- CORS;
- параметры подключения к БД.

Это позволяет использовать один и тот же код в разных окружениях без изменений:

```
Development → Docker Compose → Production

```

## 8. Технологический стек

**Язык и серверная часть**
- Go — основной язык реализации
- `net/http` — HTTP-сервер
- Gorilla Mux — маршрутизация запросов
- `context` — управление временем жизни запросов и таймаутами
- goroutines и channels — запуск сервера и graceful shutdown

**База данных**
- PostgreSQL
- `database/sql`, `lib/pq`
- connection pooling
- автоматическое создание схемы + seed из dump

---

## 9. Ключевая архитектурная особенность

Auth Service — точка управления учетной записью, но сами пользовательские данные распределены между сервисами: аутентификация (Auth Service) отделена от профиля (User Service) и от членства в чатах (Chat Service). Взаимодействие между сервисами происходит исключительно через HTTP API, что сохраняет независимость их баз данных.
