# Chat Service — техническая документация

Микросервис мессенджера **Sozvon**, отвечающий за создание и управление чатами, обмен сообщениями в реальном времени, историю переписки, статусы прочтения, редактирование и удаление сообщений, пересылку сообщений, а также работу с файлами и изображениями.

**Архитектурный принцип:** HTTP API используется для операций с данными (команды), WebSocket — для мгновенной доставки событий подключенным клиентам.

```
						Chat Service
							│
			┌───────────────┴────────────────┐
			│                                │
		HTTP/REST                        WebSocket
			│                                │
			▼                                ▼
	команды и данные                событие в real-time
			│                                │
	┌───────┼────────┐            ┌──────────┼─────────┐
	│       │        │            │          │         │
 создание история  файлы       new msg     typing    edited
```

## 1. HTTP API

### 1.1 Чаты

| Метод / путь | Описание |
|---|---|
| `POST /api/chats/create` | Создание чата (`direct` или `group`) |
| `GET /api/chats` | Список чатов текущего пользователя |
| `GET /api/chats/{chatId}` | Участники чата и их online-статус |

**Создание чата:**
- `group` — задается название и список участников; создатель автоматически добавляется в список.
- `direct` — перед созданием проверяется наличие существующего диалога, повторное создание не требуется.
- После создания всем участникам рассылается WebSocket-событие `chat:created`, что избавляет клиента от необходимости опрашивать сервер.

**Online-статус** определяется через WebSocket Hub: наличие активного соединения пользователя = пользователь online.

### 1.2 Сообщения

| Метод / путь | Описание |
|---|---|
| `POST /api/chats/{chatId}/messages` | Отправка сообщения |
| `GET /messages` | Первоначальная загрузка истории |
| `GET /messages/before` | Подгрузка более старых сообщений |
| `GET /messages/after` | Получение новых сообщений после указанного |
| `GET /messages/{messageId}/context` | Контекст вокруг конкретного сообщения |
| `PUT /api/chats/{chatId}/messages/{messageId}` | Редактирование сообщения |
| `DELETE /api/chats/{chatId}/messages/{messageId}` | Удаление сообщения |
| `POST /api/chats/forward` | Пересылка сообщений в другой чат |

**Порядок отправки сообщения:**
1. Извлечение `user_id` из JWT
2. Проверка членства пользователя в чате
3. Валидация сообщения
4. Сохранение сообщения
5. Активация чата (если требуется)
6. Получение списка участников
7. Рассылка события `message:new` всем участникам, кроме отправителя

- Поддерживается ответ на сообщение через поле `replyToId`.
- Пагинация: `limit` + `offset`, размер страницы по умолчанию **50**, максимум **200**.

**Редактирование** — доступно только автору; после изменения рассылается `message:edited` (chatId, messageId, новый текст).

**Удаление** — доступно только автору; вместе с сообщением удаляются связанные файлы из файлового хранилища; рассылается `message:deleted`.

**Пересылка** (`/api/chats/forward`):
- можно переслать несколько сообщений одновременно;
- можно добавить собственный комментарий;
- вложения пересылаемых сообщений передаются вместе с ними;
- новые сообщения также рассылаются через `message:new`.

### 1.3 Непрочитанные сообщения

| Метод / путь | Описание |
|---|---|
| `GET /api/chats/{chatId}/messages/unread` | Первое непрочитанное, количество, сообщения вокруг точки, наличие истории выше/ниже |
| `POST /api/chats/{chatId}/read` | Отметить сообщения чата прочитанными |

Логика построена вокруг курсора `last_read_message_id` (см. раздел БД).

### 1.4 Файлы

| Метод / путь | Описание |
|---|---|
| `POST /api/chats/{chatId}/upload` | Отправка сообщения с вложениями |
| `GET /api/media/{filename}` | Получение файла |

- `upload` поддерживает: текст, несколько файлов, ответ на сообщение, метаданные изображения (`width`, `height`).
- Ограничения: максимальный размер файла + `MaxBytesReader` на весь HTTP body.
- После сохранения формируется `attachment`: имя, MIME-тип, размер, URL.
- При отдаче файла (`GET /api/media/{filename}`) проверяется имя файла на path traversal (`..`, `/`).

## 2. WebSocket (real-time)

### 2.1 Подключение

```
/ws?token=<JWT>
```

Перед установкой соединения JWT проверяется, из него извлекается `user_id`. После успешной аутентификации создается объект `Client`, регистрируемый в центральном **WebSocket Hub**.

```
              ┌──────────────────┐
              │   Chat Service   │
              │                  │
Client A ──WS──►                 │
Client B ──WS──►      Hub        │
Client C ──WS──►                 │
              │                  │
              └────────┬─────────┘
                       │
                   PostgreSQL
```

Hub хранит активные соединения через `sync.Map`: `userID → *Client` — позволяет быстро определить, подключен ли пользователь.

### 2.2 Горутины клиента

- `readPump()` — получает сообщения от клиента;
- `writePump()` — отправляет сообщения клиенту, периодически шлет `Ping`.
- `PongHandler` обновляет `ReadDeadline` — разорванные/не отвечающие соединения обнаруживаются автоматически.

### 2.3 События

| Событие | Когда отправляется |
|---|---|
| `chat:created` | После создания чата |
| `chat:activated` | При активации чата |
| `message:new` | Новое/пересланное сообщение |
| `message:edited` | Редактирование сообщения |
| `message:deleted` | Удаление сообщения |
| `typing:start` / `typing:stop` | Индикатор набора текста |
| `error` | Ошибка |

**Поток события на примере отправки сообщения:**
```
POST /messages → сохранение → Hub.SendToUsers(...) → WebSocket → клиенты участников
```

**Индикатор набора текста:** при `typing:start`/`typing:stop` сервис получает `chatId`, находит участников чата и рассылает остальным событие с `fromId` («Александр печатает...»).

## 3. База данных

### 3.1 Структура сущностей

```
chats
 │
 ├── chat_members
 │
 └── messages
      │
      ├── attachments
      │
      └── forwarded_attachments
```

### 3.2 Таблицы

**`chats`**
- `id`, `active`, `created_at`, `type` (`direct` / `group`), `name`
- `active` управляет состоянием: чат может быть создан заранее и активирован только после первого сообщения.
- Создание выполняется в транзакции: `INSERT chats` → `INSERT chat_members` (для каждого участника) → `COMMIT`; при ошибке — `ROLLBACK`.

**`chat_members`**
- `chat_id`, `user_id`, `last_read_message_id`
- Составной первичный ключ `(chat_id, user_id)` — пользователь не может быть добавлен в чат дважды.
- Используется для: определения участников, проверки прав на отправку, удаления пользователя из всех чатов, хранения позиции прочтения.
- `last_read_message_id` — курсор прочтения:

  ```
  message 1
  message 2
  message 3 ← last_read_message_id
  message 4 ← unread
  message 5 ← unread
  ```
  По нему вычисляется количество непрочитанных и область истории вокруг первого непрочитанного.

**`messages`** — центральная таблица сервиса
- `id`, `chat_id`, `sender_id`, `text`, `created_at`
- `reply_to_id` — ответ на сообщение (при загрузке истории делается `LEFT JOIN` на саму таблицу для preview оригинала); `ON DELETE SET NULL` — удаление исходного сообщения не ломает ответ, ссылка становится `NULL`.
- `edited_at` — время редактирования (изменить может только автор: `WHERE id = $2 AND sender_id = $3`).
- `deleted_at` — при удалении также каскадно удаляются `attachments` (`ON DELETE CASCADE`).
- `forwarded_sender_id`, `forwarded_text`, `forwarded_from_message_id` — snapshot исходного сообщения при пересылке; сохраняет информацию об оригинале даже при его последующем изменении. При повторной пересылке уже пересланного сообщения берется исходный snapshot, а не создается цепочка вложенных ссылок.

**`attachments`**
- `id` (UUID, `uuid.NewString()`), `message_id`, `file_name`, `store_name`, `mime_type`, `size`, `width`, `height`
- Файл физически не хранится в PostgreSQL — только метаданные:
  ```
  PostgreSQL → metadata файла
  File Storage → физический файл
  ```

**`forwarded_attachments`**
- `message_id`, `attachment_id`, составной PK `(message_id, attachment_id)`
- Связывает пересланное сообщение с уже существующими вложениями — физический файл не копируется повторно:
  ```
  Original Message
       │
       ├── attachments ── file1, file2
       ▼
  Forwarded Message
       │
       └── forwarded_attachments ── file1, file2
  ```

### 3.3 Пагинация сообщений

Операции: `GetChatMessages()`, `GetMessagesBeforeID()`, `GetMessagesAfterID()`, `GetMessagesAroundID()`.
Критерий сортировки — `created_at`:

```
← старые              новые →
100 101 102 103 104 105 106 107
                ↑
         текущее сообщение
```

Можно запросить сообщения ДО / ПОСЛЕ / ВОКРУГ заданного. Для ускорения — индекс `idx_messages_chat_id_created (chat_id, created_at)`.

### 3.4 Транзакции

Используются там, где несколько операций должны быть атомарны:
- создание чата (`INSERT chats` + `INSERT chat_members` × N);
- пересылка нескольких сообщений.

При ошибке — `ROLLBACK`, частично выполненные изменения не сохраняются.

### 3.5 Каскадное удаление

| Связь | Поведение |
|---|---|
| `chats → chat_members` | `ON DELETE CASCADE` |
| `messages → attachments` | `ON DELETE CASCADE` |
| `messages.reply_to_id` | `ON DELETE SET NULL` |

### 3.6 Индексы

```
idx_attachments_message_id
idx_messages_chat_id_created
idx_messages_reply_to
idx_messages_forwarded_from
idx_chats_active
idx_chats_type
idx_chat_members_user_id
idx_chat_members_last_read
idx_messages_deleted_at
```

Ориентированы на: выборку сообщений чата, поиск участников, работу с attachments, непрочитанные сообщения, поиск связанных сообщений, фильтрацию активных чатов.

### 3.7 Миграции

- Выполняются автоматически при запуске сервиса, в транзакции.
- Создают таблицы: `chats`, `messages`, `chat_members`, `attachments`, `forwarded_attachments`, затем индексы.
- Используют `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` — повторный запуск безопасен.
- Предусмотрено начальное заполнение БД из дампа `db/chatdb_dump.sql`.

## 4. Аутентификация

- Chat Service самостоятельно проверяет JWT (собственной системы паролей не имеет — использует токены, выданные Auth Service).
- HTTP: `Authorization: Bearer <token>`.
- WebSocket: query-параметр `token`.
- Из JWT извлекаются: `UserID`, `Login`, `Name`.
- `UserID` используется для проверки членства в чатах и определения авторства сообщений.

## 5. Надежность

### Middleware
- **Logging** — журналирование HTTP-запросов;
- **Recovery** — перехват panic.

### Таймауты
- `context.WithTimeout` для операций;
- HTTP-сервер: `ReadTimeout`, `WriteTimeout`, `IdleTimeout`.

### Ограничения WebSocket
- максимальный размер сообщения;
- размеры read/write buffer;
- `WriteWait`, `PongWait`, `PingPeriod`.

### Буферизация
- канал клиента `send chan models.WSMessage` — 256 сообщений;
- общий broadcast-канал Hub — 1024 сообщения.

Это предотвращает блокировку основного потока при обычных пиковых нагрузках.

### Graceful shutdown

При получении `SIGINT`/`SIGTERM`:
1. Получение сигнала завершения
2. Остановка WebSocket Hub
3. Закрытие активных WebSocket-соединений
4. Ожидание завершения Hub (через `WaitGroup`)
5. Корректное завершение HTTP-сервера (`http.Server.Shutdown()`)

## 6. Технологический стек

**Backend**
- Go — основной язык
- `net/http` — HTTP-сервер

**API**
- REST/HTTP, JSON
- WebSocket
- `multipart/form-data` для файлов

## 7. Ключевая архитектурная особенность

Сочетание **REST API** (команды и данные: создание, история, файлы) и **WebSocket** (события в real-time: новые сообщения, typing, edited) позволяет избежать постоянного polling со стороны клиента — после отправки сообщения сервер сразу уведомляет всех участников с активным WebSocket-соединением.
